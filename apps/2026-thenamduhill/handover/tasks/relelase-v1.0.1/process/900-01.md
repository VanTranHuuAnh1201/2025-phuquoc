## 1. Triệu chứng tái hiện được

**Không suy đoán từ đọc code** — đo trực tiếp bằng lời gọi RPC thật:

```
POST /api/bookings/<id>/refund   { amount: 100000, paymentMethod: 'bank-transfer' }
→ HTTP 500  { "code": "INTERNAL_ERROR" }
```

Nguyên nhân gốc, lấy từ lỗi Postgres trả về:

```
23514  new row for relation "activity_logs"
       violates check constraint "chk_logs_action"
Failing row: (..., 'refund-processed', 'paid_amount', '573750.00', '573749.00', ...)
```

`refund_booking_payment()` ghi `action = 'refund-processed'`, nhưng:

```sql
chk_logs_action CHECK (action = ANY (ARRAY[
  'created', 'status-changed', 'payment-recorded', 'checked-in',
  'checked-out', 'note-added', 'room-assigned', 'price-adjusted', 'cancelled'
]))
```

**9 giá trị hợp lệ, KHÔNG có `'refund-processed'`.**

## 2. Ảnh hưởng thực tế

| | |
|---|---|
| Mức độ | **Chức năng hoàn tiền hỏng 100%** — không phải lỗi thỉnh thoảng |
| Ai chịu | `owner` / `manager` (hai vai duy nhất có `booking.refund`) |
| Người dùng thấy gì | *"Hệ thống gặp sự cố. Thử lại sau ít phút."* — thử lại bao nhiêu lần cũng vậy |
| Nghiệp vụ kẹt | Khách huỷ đơn đúng chính sách §B5, `/cancel/quote` tính đúng số tiền hoàn, nhưng **không có đường nào chi tiền ra**. Phải xử lý tay ngoài hệ thống ⇒ sổ sách lệch |

**Tin tốt duy nhất**: transaction rollback nguyên vẹn — `paid_amount` không bị
trừ, không đơn nào lệch sổ. Đã kiểm bằng cách đọc lại DB sau lần gọi lỗi.

**Vì sao build vẫn xanh**: TypeScript không kiểm được CHECK constraint nằm trong
Postgres. Đây **cùng họ** với bug `chk_payments_method` (`bank_transfer` gạch
dưới vs `bank-transfer` gạch ngang) đã nêu ở §1 ticket `400-01` — đúng loại lỗi
chỉ integration test gọi thật vào DB mới bắt được.

## 6. Kỹ thuật — *`ndh-sa` điền*

**Chốt hướng A** — mở rộng `chk_logs_action`, không đổi giá trị RPC ghi.

Lý do quyết định (không phải sở thích, mà là hệ quả nghiệp vụ): `ActivityLog` tồn
tại để làm bằng chứng khi tranh chấp với khách (§B1). Hướng B ghi hoàn tiền dưới
mã `payment-recorded` sẽ làm nhật ký **mất chiều tiền** — đọc lại sổ không phân
biệt được lần nào thu vào, lần nào chi ra. Đó đúng là câu hỏi mà nhật ký sinh ra
để trả lời, nên tiết kiệm một dòng migration bằng cách bỏ nó đi là lỗ.

Chi phí hướng A đúng bằng: 1 file migration + 1 giá trị trong `LogAction`.

**Ba chỗ phải khớp nhau, sửa cùng lúc** (BE8 — SQL là nguồn sự thật):

| # | Chỗ | Thay đổi |
|:--:|---|---|
| 1 | `chk_logs_action` (Postgres) | 9 → 10 giá trị, thêm `refund-processed` |
| 2 | `LogAction` — `packages/core/src/booking-types.ts` | thêm `'refund-processed'` |
| 3 | `refund_booking_payment()` | **giữ nguyên** — nó đang ghi đúng ngữ nghĩa |

**Ràng buộc thi hành:**

- Migration là **file mới** `20260103000000_add_refund_processed_log_action.sql`
  (BE7). `DROP CONSTRAINT IF EXISTS` rồi `ADD CONSTRAINT` trong một `BEGIN/COMMIT`.
- **Không** đụng `api-contracts.ts` (đã FREEZE) — bug này nằm dưới tầng hợp đồng,
  shape response `/refund` không đổi. Chuẩn hoá shape là `390-07`.
- Rủi ro #2 của mục 7 là bắt buộc, không phải tuỳ chọn: rà **cả 6 RPC** bằng
  `pg_get_functiondef()` trên DB thật, không grep file `.sql` (file có thể lệch
  với DB — xem migration `20260808092418` chỉ có trên DB, ghi ở MAP §6).

## 9. Bàn giao — *`ndh-be` điền khi xong*

### Nguyên nhân gốc (đo trên DB thật, không suy từ code)

`chk_logs_action` nhận **đúng 9** giá trị:

```
created · status-changed · payment-recorded · checked-in · checked-out
note-added · room-assigned · price-adjusted · cancelled
```

Kiểm bằng cách insert thử từng giá trị vào `activity_logs`: 9 giá trị trên
ACCEPT; `refund-processed`, `refunded`, `payment-refunded` đều REJECT `23514`.
`refund_booking_payment()` ghi `refund-processed` ⇒ nổ ⇒ rollback cả RPC ⇒ route
bắt `rpcError` rồi trả `serverError()` ⇒ **500 mọi lần**.

### File đã sửa

| File | Thay đổi |
|---|---|
| `supabase/migrations/20260103000000_add_refund_processed_log_action.sql` | **MỚI.** `chk_logs_action` 9→10 giá trị. Dọn 10 dòng `actor_id='PROBE'` do lần dò constraint để lại |
| `packages/core/src/booking-types.ts` | `LogAction` thêm `'refund-processed'` (BE8) |
| `apps/2026-thenamduhill/tests/api/booking-lifecycle.test.ts` | Đảo test khoá bug sang happy path (AC-5) + thêm 1 negative |
| `handover/tasks/release-v1.0.0/API_INTEGRATION_MAP.md` | `/refund` 🔴→✅, `BE ✅` 17→18, §0 + §3 + §6 |

**Không sửa** `refund_booking_payment()`, không sửa route `/refund`, không đụng
`api-contracts.ts` (FREEZE), không đụng `packages/theme-*`.

### Rà 6 RPC — rủi ro #2 của mục 7

Đọc `pg_get_functiondef()` của mọi function trong `public` trên DB thật, tách
literal ở **đúng vị trí cột `action`** của từng `INSERT INTO activity_logs`
(regex thô cho ra dương tính giả `'at'` từ `jsonb_build_object('at', NOW())` —
phải parse theo vị trí cột, không grep thẳng).

| RPC | `action` ghi | |
|---|---|:--:|
| `create_booking_atomic` | `created` | ✅ |
| `check_in_booking` | `room-assigned`, `status-changed` | ✅ |
| `confirm_booking_payment` | `payment-recorded`, `status-changed` | ✅ |
| `check_out_booking` | `status-changed` | ✅ |
| `cancel_booking` | `status-changed` | ✅ |
| `refund_booking_payment` | `refund-processed` | ✅ *(sau migration)* |

**8/8 vị trí hợp lệ — `/refund` là chỗ duy nhất vi phạm.** 3 chỗ ghi log bằng TS
(`cron/no-show`, `cron/release-holds`, `webhooks/payment`) đều ghi `status-changed`.
Dữ liệu đang có trong `activity_logs` cũng chỉ dùng 7 giá trị hợp lệ ⇒ constraint
mới không làm hỏng dòng cũ nào.

Đã đối chiếu `RefundBookingResponse` trong `api-contracts.ts` (dòng 936) với thứ

— tức nó mô tả đúng row `bookings` mà RPC trả thẳng ra. **Không lệch**, không cần
đụng hợp đồng đã FREEZE. Việc chuẩn hoá shape `/cancel` + `/refund` vẫn thuộc
`390-07` (nợ `M33`) như mục 3 đã khai.

`BOOKING_NOT_FOUND` (404), 401/403, `InternalError` — 4 case test đang phủ 3 mã
đầu.

### Nợ mới `M39` — test KM rò dữ liệu, làm 3 case đỏ ngẫu nhiên (ngoài phạm vi)

**Phát hiện khi chạy `pnpm test:api` nhiều lần để verify `900-01`.** Ghi lại vì
luật A5 cấm giấu lỗi phát hiện ngoài phạm vi.

**Triệu chứng tái hiện được**: chạy riêng `pnpm vitest run tests/api/availability.test.ts`
→ **2 failed / 10 passed**, dù không ai sửa file đó. Chạy lại lần nữa, tập case
đỏ **đổi khác** — lúc `expected +0 to be 280000`, lúc `expected 720000 to be 200000`,
lúc lan sang `bookings.test.ts` `expected 384000 to be 600000`.

**Nguyên nhân** (đọc thẳng bảng `promotions` sau khi test chạy xong):
`availability.test.ts` tạo KM `zz-test-*` với `active=true`, `code=NULL` nhưng
**teardown không xoá chúng**. KM không có `code` là KM **tự động áp** ⇒ mọi báo
giá của các case sau — kể cả file test khác — bị trừ thêm tiền không mong đợi.
`withAutoPromotionsDisabled()` (`tests/helpers/seed.ts:293`) chỉ tắt KM seed và
**cố ý bỏ qua** id bắt đầu bằng `zz-test-` (dòng 304), nên rác này không bị chặn.

Chúng cũng **không xoá được** bằng `DELETE`: `23503 booking_promotions_promotion_id_fkey`.

**Lỗi có từ trước `900-01`**, không do thay đổi này — file `availability.test.ts`
không nằm trong diff của ticket.

**Cách sửa đúng**: teardown của `availability.test.ts` phải `UPDATE promotions SET
active=false WHERE id LIKE 'zz-test-%'` (tắt, không xoá — có khoá ngoại từ
`booking_promotions`). Cần `ndh-sa` quyết mở ticket riêng hay gộp vào `M36`
(đang sửa chính tầng khuyến mãi).

**Dọn tạm để chạy lại xanh**: tắt các KM `zz-test-*` còn sót rồi chạy lại — đã
làm, suite trở về **85/85 xanh**.
