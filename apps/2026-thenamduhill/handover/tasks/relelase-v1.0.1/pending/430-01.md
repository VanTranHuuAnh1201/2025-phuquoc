## 1. Bối cảnh — đây là bug đang chờ nổ, không phải cải tiến

Route `/api/admin/upload` hiện ghi vào `public/uploads/`. Chính comment trong file
đã cảnh báo (đọc [route.ts:19-25](../../../../src/app/api/admin/upload/route.ts#L19-L25)):

> *"filesystem của Vercel là **ephemeral** — ảnh tải lên sẽ MẤT sau mỗi lần deploy,
> và hai instance serverless không thấy file của nhau."*

Nghĩa là: chị tải 30 ảnh phòng lên, em deploy một bản sửa lỗi, **30 ảnh biến mất**.
Đây là quyết định "nhanh nhất, nâng cấp sau" đã chốt ở v1.0.0 — giờ là lúc nâng cấp.

Đường nâng cấp đã chừa sẵn: **chỉ đổi thân hàm `persist()`**, hợp đồng
request/response **không đổi** nên CMS không phải sửa dòng nào.

## 2. Phạm vi

**Trong:** đổi `persist()` sang Supabase Storage · sinh 4 kích thước · xuất
WebP + AVIF · trả `srcset` trong response · giữ nguyên hợp đồng API.

**Ngoài:** giao diện kéo-thả → `430-02`.

## 3. Dữ liệu vào / ra

`sharp` đã có trong `package.json` — không cài mới.

**Request: KHÔNG ĐỔI** (`multipart/form-data`, field `file`).

**Response: mở rộng thêm field, không xoá field cũ** — để CMS hiện tại vẫn chạy:

```ts
{
  success: true,
  data: {
    url: '/...',              // GIỮ NGUYÊN — kích thước lớn nhất, CMS cũ dùng field này
    width: 2000,              // GIỮ NGUYÊN
    height: 1333,             // GIỮ NGUYÊN
    // ── MỚI ──
    srcSet: {
      avif: '... 480w, ... 960w, ... 1440w, ... 2000w',
      webp: '... 480w, ... 960w, ... 1440w, ... 2000w',
    },
    blurDataURL: 'data:image/webp;base64,…',   // placeholder mờ khi đang tải
  },
  error: null
}
```

Đường dẫn: `media/{yyyy}/{mm}/{slug}-{hash}-{w}.{ext}`

4 bề ngang: **480 · 960 · 1440 · 2000**. Không phóng to ảnh nhỏ hơn
(`withoutEnlargement`, đã có trong code hiện tại).

## 5. Tiêu chí chấp nhận (AC)

| # | AC | Kiểm bằng |
|:--:|---|---|
| 1 | **Ảnh còn sống sau một lần deploy thật** — tải ảnh lên, deploy, mở lại URL cũ | Deploy thật + ảnh chụp |
| 2 | **Hợp đồng request không đổi** — CMS hiện tại upload được **không sửa dòng nào** | `git diff` không chạm file CMS |
| 3 | `data.url` vẫn có và vẫn dùng được (không phá CMS cũ) | 1 case tầng 2 |
| 4 | Mỗi ảnh sinh **4 kích thước × 2 định dạng = 8 file** | Đếm object trong bucket |
| 5 | `srcSet` đúng cú pháp `w`, thứ tự tăng dần | Assert bằng regex |
| 6 | Ảnh nhỏ hơn 480px → **chỉ sinh 1 kích thước**, không phóng to | 1 case |
| 7 | `blurDataURL` là data URI hợp lệ, dưới 2KB | 1 case |
| 8 | **Negative**: SVG bị loại (có thể chứa script) → **400** | 1 case |
| 9 | **Negative**: file vượt `MAX_BYTES` (15MB) → **400**, không phải 500 | 1 case |
| 10 | **Negative**: file không phải ảnh (đổi tên `.exe` thành `.jpg`) → **400** — kiểm bằng magic bytes, không tin `content-type` | 1 case |
| 11 | **Negative**: gọi không quyền `content.edit` → **403** | 1 case |
| 12 | Giữ `withAuthGuard(..., 'content.edit')` — không nới quyền | Đọc code |
| 13 | Tên file vẫn chống path traversal + chống ghi đè (logic `safeName` hiện có) | 2 case: tên có `../`, hai file trùng tên |
| 14 | **Ảnh 8MB từ điện thoại upload xong dưới 10 giây** | Đo thật, ghi số |
| 15 | Lỗi Storage → trả lỗi **song ngữ** rõ ràng, **không nuốt** (luật C3) | 1 case |
| 16 | `pnpm test` xanh, lint/typecheck sạch, 0 `any` | Chạy lệnh |

## 6. Kỹ thuật — *`ndh-sa` điền*

> ⬜ Cần chốt: bucket public hay signed URL (xem `M27` — public thì mọi ảnh truy
> cập được bằng URL trực tiếp; với ảnh marketing thì đúng)? Sinh 8 biến thể đồng
> bộ trong request (chậm hơn nhưng đơn giản) hay bất đồng bộ qua queue? Với ảnh
> 8MB và trần 10s ở AC-14, `ndh-sa` chốt cách nào chắc chắn đạt.

## 7. Rủi ro

| # | Rủi ro | Cách chặn |
|---|---|---|
| 1 | Sinh 8 biến thể trong một request → timeout serverless (Vercel mặc định 10s) | AC-14 đo thật. Nếu không đạt, `ndh-sa` chốt phương án bất đồng bộ. **Không được để timeout im lặng** |
