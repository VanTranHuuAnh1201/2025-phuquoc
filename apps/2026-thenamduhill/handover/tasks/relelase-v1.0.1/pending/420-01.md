## 1. Bối cảnh

Chị yêu cầu: *"nếu giai đoạn đầu chưa cần triển khai thì mình thiết kế theo hướng
để sau này tích hợp dễ dàng là được"*. Đây chính xác là ticket đó.

**Vì sao phải làm BÂY GIỜ chứ không để v1.1:** nếu inventory và booking không ghi
outbox từ đầu, sau này nối Channel Manager phải **sửa lại 5 RPC lifecycle** — đúng
thứ luật R5 cấm ("thêm tính năng không được sửa code sẵn có"). Sửa RPC đã chạy
production là việc rủi ro nhất trong cả hệ thống, vì nó chạm vào chống overbooking.

Làm bây giờ: thêm 1 bảng + 1 dòng `INSERT` trong mỗi RPC. Làm sau: mở lại 5 RPC
đang giữ tiền thật của khách.

## 2. Phạm vi

**Trong:** bảng `integration_outbox` · ghi event trong 5 RPC lifecycle + mọi chỗ
ghi `inventory` · cron dọn theo retention.

**Ngoài:** gửi event đi đâu → `420-02` · màn hình CMS → `420-03`.

## 3. Dữ liệu vào / ra

```sql
-- supabase/migrations/<timestamp>_integration_outbox.sql
create table integration_outbox (
    id            uuid primary key default gen_random_uuid(),
    event_type    text not null,      -- 'booking.created' | 'booking.confirmed' |
                                      -- 'booking.cancelled' | 'booking.checked_in' |
                                      -- 'booking.checked_out' | 'inventory.changed'
    aggregate_id  uuid not null,      -- booking_id hoặc room_type_id
    payload       jsonb not null,
    status        text not null default 'pending',  -- pending | sent | failed | dead
    attempts      int  not null default 0,
    last_error    text,
    next_retry_at timestamptz,
    created_at    timestamptz not null default now(),
    updated_at    timestamptz not null default now()
);
```

Mỗi bảng phải có `id`, `created_at`, `updated_at` (luật BE7). Migration đi **một
chiều** — không sửa file đã chạy.

## 5. Tiêu chí chấp nhận (AC)

| # | AC | Kiểm bằng |
|:--:|---|---|
| 1 | Migration mới, **không sửa file migration cũ** (luật BE7) | `git diff` trên `supabase/migrations/` |
| 2 | Bảng có RLS policy — **chỉ service role đọc/ghi**, khách và staff không thấy | pgTAP: đổi vai → 0 rows |
| 3 | **Đặt 1 đơn → đúng 1 dòng `booking.created`** — không 0, không 2 | pgTAP |
| 4 | Cả 5 chuyển trạng thái sinh đúng event tương ứng | pgTAP, 5 case |
| 5 | Ghi `inventory` (đổi giá, đóng bán, đổi số phòng) → sinh `inventory.changed` | pgTAP, 3 case |
| 6 | **Ghi outbox nằm TRONG cùng transaction** với RPC — RPC rollback thì outbox rollback theo | pgTAP: ép RPC lỗi → 0 dòng outbox |
| 7 | **Negative**: ghi outbox thất bại **không được** làm RPC đặt phòng thất bại theo... | xem AC-8 |
| 8 | ...**trừ khi** đó là vi phạm nhất quán. `ndh-sa` chốt: outbox trong transaction (nhất quán, AC-6) là **ưu tiên** — chấp nhận đơn fail nếu outbox fail, vì mất event nghĩa là lệch phòng trên OTA | `ndh-sa` ghi kết luận mục 6 |
| 9 | `payload` chứa đủ dữ liệu để adapter dựng lại lệnh đồng bộ **không cần query thêm** | Đọc 1 payload thật |
| 10 | Retention 90 ngày + cron dọn, **cùng migration** | Đọc migration |
| 11 | Index trên `(status, next_retry_at)` để cron quét nhanh | `\d integration_outbox` |
| 12 | pgTAP ≥8 case, ≥3 negative | Đếm |
| 13 | `pnpm test:sql` + `test:api` xanh, lint/typecheck sạch | Chạy lệnh |

## 6. Kỹ thuật — *`ndh-sa` điền*

> ⬜ **Cần chốt dứt điểm AC-7/AC-8**: outbox trong cùng transaction (nhất quán,
> đơn fail nếu outbox fail) hay ngoài transaction (đơn luôn thành công, có thể
> mất event)?
>
> Khuyến nghị của em: **trong transaction**. Mất một event `inventory.changed`
> nghĩa là OTA vẫn mở bán phòng đã bán → overbooking trên Booking.com, và đó là
> thứ không sửa được bằng lời xin lỗi. Đơn fail thì khách đặt lại được.
