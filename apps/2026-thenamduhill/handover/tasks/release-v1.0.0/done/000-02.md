## 4. Quyết định thiết kế

### 4.1 Một bảng `accounts`, không tách hai

Lý do không tách bảng `users` (admin) và `customers` (khách):

- TS đã mô hình đúng vậy: `Customer extends Account` (`booking-types.ts:488`), chỉ thu hẹp `role: 'customer'` và thêm `totalSpent`, `stayCount`.
- `bookings.customer_id` phải trỏ vào **một** chỗ. Tách hai bảng thì lễ tân đặt hộ khách qua điện thoại (`booking_source = PHONE`) không biết gắn vào đâu.
- Truy vấn "ai được xem đơn này" phải `UNION` hai bảng.
- Thêm vai trò thứ sáu sau này là thêm bảng thứ ba.

```sql
CREATE TABLE public.accounts (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    role VARCHAR(20) NOT NULL,
    full_name VARCHAR(255) NOT NULL DEFAULT '',
    phone VARCHAR(50) UNIQUE,
    email VARCHAR(255) UNIQUE,
    password_hash VARCHAR(255),      -- NULL với khách đăng nhập bằng OTP
    is_active BOOLEAN DEFAULT TRUE NOT NULL,

    -- chỉ có ý nghĩa khi role = 'customer'
    total_spent DECIMAL(14,2) DEFAULT 0 NOT NULL,
    stay_count INT DEFAULT 0 NOT NULL,
    internal_note TEXT,

    created_at TIMESTAMPTZ DEFAULT NOW() NOT NULL,
    updated_at TIMESTAMPTZ DEFAULT NOW() NOT NULL,

    CONSTRAINT chk_role CHECK (role IN ('owner','manager','receptionist','editor','customer')),
    CONSTRAINT chk_identity CHECK (phone IS NOT NULL OR email IS NOT NULL),
    CONSTRAINT chk_staff_password CHECK (role = 'customer' OR password_hash IS NOT NULL)
);
```

Ràng buộc cuối bắt buộc nhân viên phải có mật khẩu, khách thì không cần.

## 6. Ghi chú kỹ thuật (SA)

`permissions.ts` phải là **hàm thuần**, không đọc trạng thái toàn cục, không gọi API. Nó chỉ trả lời *"vai trò X có quyền Y không"*. Việc lấy vai trò hiện tại là của tầng gọi.

RLS policy phải viết bằng vai trò Postgres, **không dựa vào biến do client gửi lên**. Nếu dùng Supabase Auth thì đọc từ `auth.jwt()`; nếu tự quản lý JWT thì đặt `SET LOCAL` trong transaction sau khi verify token ở server.

Không dùng bảng `users` như schema nháp đề xuất — thống nhất tên `accounts` cho khớp TS.

Ticket này **chỉ thiết kế và viết `permissions.ts`**. Việc gắn `can()` vào từng API route thuộc về `000-03` và các ticket giai đoạn 200.

### 6.1 Chữ ký chốt của `packages/core/src/permissions.ts`

Viết **đúng** như dưới đây. BE không tự thêm/bớt permission — thiếu thì mở ticket mới.

```ts
import type { Role } from './booking-types'

/**
 * Nguồn sự thật duy nhất về quyền (luật A3 / BE2).
 * Hàm thuần, không đọc trạng thái toàn cục, không gọi API, không import React.
 */
export type Permission =
    // đơn hàng
    | 'booking.view.all'
    | 'booking.view.own'
    | 'booking.create'
    | 'booking.change-status'
    | 'booking.cancel'
    | 'booking.cancel.own'
    | 'booking.refund'
    | 'booking.surcharge'
    // tồn kho & giá
    | 'inventory.view'
    | 'inventory.edit'
    | 'price.view'
    | 'price.edit'
    | 'promotion.view'
    | 'promotion.edit'
    // nội dung
    | 'content.edit'
    // hệ thống
    | 'account.manage'
    | 'settings.bank'
    | 'report.view'
    | 'report.view.full'

export const ALL_PERMISSIONS: readonly Permission[] = [ /* 20 mục, đúng thứ tự trên */ ]

export const ROLE_PERMISSIONS: Record<Role, readonly Permission[]> = { /* §6.2 */ }

/** Vai trò X có quyền Y không. Đây là hàm duy nhất mọi tầng được gọi. */
export function can(role: Role, permission: Permission): boolean

/** Có ÍT NHẤT MỘT trong các quyền. Dùng cho màn hình đọc nhiều nguồn. */
export function canAny(role: Role, permissions: readonly Permission[]): boolean

/** Có ĐỦ MỌI quyền. Dùng cho thao tác ghi chạm nhiều bảng (vd check-out vừa đổi trạng thái vừa thu phụ phí). */
export function canAll(role: Role, permissions: readonly Permission[]): boolean

/** Toàn bộ quyền của một vai trò — `/api/auth/me` trả mảng này cho FE ẩn/hiện nút. */
export function permissionsOf(role: Role): readonly Permission[]
```

**Chốt: CÓ làm `canAny()` và `canAll()`.** Lý do — không có chúng thì Route Handler
viết `can(r,'a') || can(r,'b')` rải rác, mỗi chỗ một kiểu, và `requirePermission()`
ở `000-03` không nhận được mảng. Cả hai là wrapper 1 dòng quanh `can()`, không
sinh thêm nguồn sự thật.

`permissionsOf()` bắt buộc vì `/api/auth/me` (`000-03` §3) trả `{ account, permissions }`
— FE đọc mảng này chứ **không** tự suy từ `role`.

Ba điểm bắt buộc khi cài đặt:

1. `ROLE_PERMISSIONS` khai bằng `as const satisfies Record<Role, readonly Permission[]>`
   — thiếu một vai trò là lỗi biên dịch, không phải lỗi chạy.
2. `can()` **không** có nhánh đặc biệt `if (role === 'owner') return true`. Owner
   được liệt kê đủ 20 quyền trong bảng. Nhánh tắt là chỗ quyền âm thầm sinh ra
   khi thêm permission mới.
3. Không export mutable array — dùng `readonly` để tầng gọi không `push()` thêm quyền.

### 6.3 Cơ chế truyền identity vào RLS — CHỐT: tự quản JWT + `service_role`

Đây là điểm mục 6 cũ để mở ("nếu dùng Supabase Auth thì…"). **Chốt dứt khoát:
KHÔNG dùng Supabase Auth (`auth.users`). Dự án tự quản JWT.**

Vì sao không dùng Supabase Auth:

1. `accounts` đã có `password_hash` + ràng buộc `chk_accounts_staff_pw`
   (schema-mapping §9.6). Dùng Supabase Auth là có **hai** nơi giữ mật khẩu —
   `auth.users` và `public.accounts` — phải đồng bộ tay, đúng loại lỗi âm thầm.
2. Yêu cầu BE10 là **8 giờ cho nhân viên, 30 ngày cho khách** trong cùng một hệ
   thống. Supabase Auth đặt JWT expiry **ở cấp project**, không theo vai trò.
3. Đăng nhập khách là OTP demo `1234` (`auth.store.ts:17`), chưa có SMS
   Brandname (M3/M10 trong `MANUAL.md`). Supabase Auth OTP cần provider thật.
4. `accounts.id` là `UUID` do chính bảng sinh; ghép với `auth.users.id` là thêm
   một cột ánh xạ và một điểm lệch.

**Hệ quả bắt buộc — sửa lại policy ở schema-mapping §11:**

`auth.uid()` **không dùng được** khi không có Supabase Auth (nó đọc claim `sub`
của JWT do GoTrue ký; JWT của ta ký bằng `JWT_SECRET` riêng, PostgREST không
chấp nhận). Policy `bookings_own_read ... USING (customer_id = auth.uid())` như
viết ở §11 sẽ **luôn trả rỗng**. Thay bằng:

```sql
-- Danh tính do Route Handler đặt vào phiên sau khi ĐÃ verify JWT ở server.
-- GUC tự đặt, không phải claim của client → client không tự khai được.
CREATE OR REPLACE FUNCTION public.current_account_id() RETURNS uuid
LANGUAGE sql STABLE AS $$
    SELECT NULLIF(current_setting('app.current_account_id', TRUE), '')::uuid
$$;

CREATE POLICY bookings_own_read ON public.bookings
    FOR SELECT USING (customer_id = public.current_account_id());
```

`TRUE` ở tham số thứ hai của `current_setting` là **bắt buộc** — thiếu nó thì
truy vấn ném lỗi khi GUC chưa đặt (khách vãng lai), thay vì trả rỗng.

**Hai đường truy cập DB, không trộn:**

| Đường | Client dùng | Khi nào | RLS |
|---|---|---|---|
| **A — service role** | `SUPABASE_SERVICE_ROLE_KEY` | Mọi Route Handler đã qua `requirePermission()` | **Bỏ qua RLS** — quyền đã chặn ở tầng trên |
| **B — anon + GUC** | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Đọc dữ liệu công khai (`room_types`, `inventory`, nội dung marketing) | Áp RLS `public_read` |

Chốt phạm vi v1.0.0: **đường A là đường chính cho mọi bảng nhạy cảm.**
`SET LOCAL app.current_account_id` chỉ dùng khi Route Handler **cố ý** muốn
chạy dưới RLS như một khách cụ thể (đọc `/my-orders`) — và phải đặt **trong
cùng transaction** với truy vấn, `SET LOCAL` hết hiệu lực khi transaction kết thúc.

```
// Route Handler đọc đơn của khách — muốn RLS làm lưới chắn thứ hai
BEGIN;
  SET LOCAL app.current_account_id = '<uuid lấy từ JWT ĐÃ verify>';
  SELECT * FROM public.bookings;      -- RLS tự lọc
COMMIT;
```

⚠️ Ba điều cấm, ghi thẳng để BE không phạm:

1. **Cấm** lấy `app.current_account_id` từ header/body/query của client. Chỉ
   lấy từ payload JWT đã verify chữ ký (BE2).
2. **Cấm** để `SUPABASE_SERVICE_ROLE_KEY` lọt sang bất kỳ file nào có
   `'use client'` hoặc biến có tiền tố `NEXT_PUBLIC_`. Service role bỏ qua toàn
   bộ RLS — lộ nó là lộ cả DB.
3. **Cấm** coi RLS là lớp duy nhất. RLS là lớp thứ ba của A3; `requirePermission()`
   ở Route Handler vẫn bắt buộc kể cả khi policy đã đúng.

Vì đường A bỏ qua RLS, `permissions.ts` **chính là** cơ chế phân quyền thật của
nhân viên. Đó là lý do ticket này chặn đường (`000-03` và mọi ticket 200 phụ thuộc).

### 6.4 File RLS đặt ở đâu

### 6.7 Review vòng 2 (SA) — defect S2 và bản vá

Review vòng 1 ở §6.6 **bỏ sót một defect bảo mật**. Ghi lại đầy đủ để không tái diễn.

#### Defect S2 — `ROLE_PERMISSIONS` mutable lúc chạy ⇒ leo thang quyền

`as const satisfies` chỉ tồn tại ở **tầng biên dịch**; sau khi tsc xoá type,
mảng lúc chạy vẫn `push()` được. Nghiêm trọng hơn: `permissionsOf()` trả về
**chính tham chiếu** của `ROLE_PERMISSIONS[role]`, và tham chiếu đó đi thẳng ra
`/api/auth/me`. Tái hiện trên bản code cũ:

```js
permissionsOf('receptionist').push('price.edit', 'account.manage')
can('receptionist', 'price.edit')      // → true
can('receptionist', 'account.manage')  // → true
```

Module là singleton nên ô nhiễm **tồn tại suốt vòng đời tiến trình**, ảnh hưởng
mọi request sau đó. Không cần kẻ tấn công — một `.sort()`/`.push()` vô ý ở tầng
gọi là đủ. Vi phạm trực tiếp §6.1 điều 3 ("Không export mutable array").

#### Đính chính: bản vá SA đề xuất ban đầu KHÔNG biên dịch được

SA đề xuất `Object.freeze({...}) as const satisfies ...`. **BE phản biện đúng**:
`as const` chỉ áp lên literal, không áp lên kết quả lời gọi hàm → **TS1355**.
Ép cho qua thì `Permission` widen thành `string` và `satisfies` mất tác dụng
bảo vệ — tức là vá lỗ runtime bằng cách đục lỗ compile-time.

Cách BE dùng là đúng: `as const` **bên trong** lời gọi, `satisfies` **bên ngoài**.

```ts
export const ROLE_PERMISSIONS = Object.freeze({
    owner: Object.freeze([...] as const),
    // …
}) satisfies Record<Role, readonly Permission[]>
```

#### Kiểm chứng bản vá — chạy thật, không đọc code

| Kiểm | Kết quả |

| Phủ freeze | **13/13** cấu trúc frozen: `ALL_PERMISSIONS`, `ROLE_PERMISSIONS` + 5 mảng con, `ROLE_LABELS` + 5 object con. `mutable: 0` |
| 5 vector tấn công (ESM strict) | `push` · gán index · thay cả thuộc tính · `delete` · `sort` → **cả 5 ném `TypeError`** |
